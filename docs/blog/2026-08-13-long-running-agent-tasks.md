# 能完成一次任务之后，Agent 还要学会连续工作

最近继续用 Agent 修改它自己。

基础的工作闭环已经跑起来了：我给出目标和约束，它读取代码、修改实现、执行验证，再把结果交回来。它不一定每次都很快，但至少能相对完整地完成一个任务。

这带来了一种很具体的变化。以前，我经常在一次执行的中间接手：处理异常、补回遗漏的上下文，或者重新解释它本来已经理解过的目标。现在，这些打断少了很多，工作节奏开始变得平稳。

但我也更清楚地看见了新的边界：完整完成一个任务，和持续完成一项复杂工作，并不是同一件事。

## 长任务最怕的不是慢，而是断

一个复杂需求通常不会以一个动作结束。它会被拆成调研、设计、实现、验证、修正等多个子任务；每一个子任务的结果，又会影响下一个子任务该做什么。

如果 Agent 完成一个子任务后就停下来等待，后续的连接工作仍然落回人身上：判断当前处在什么阶段，补充下一步目标，重新恢复必要的上下文，再决定是否应该继续。单次执行看起来已经成功，整段工作却仍然被切得很碎。

这种打断的成本不只是多发几条消息。人需要重新进入问题，重新确认已做和未做的部分，也需要重新判断过程有没有偏离。任务越长，这些切换越频繁，注意力就越容易被消耗在“让工作继续”上，而不是工作本身。

所以，当 Agent 有了基础工作能力之后，我开始觉得，长任务执行的重要性不亚于再增加一个新工具。它需要的不只是能做完某一步，而是能在明确边界内，把一连串有依赖的步骤持续推进下去。

## 先处理那些不该中断的地方

目前，我先做了两项比较基础的优化。

第一项是异常重试机制。推理或调用过程偶尔会出现临时性异常，这类问题不一定意味着任务本身无法继续。如果每次异常都直接结束整次运行，人就会被迫接手一个尚未真正失败的任务。加入重试后，Agent 可以先在有限次数内恢复这类瞬时故障；只有确认无法恢复时，才把中断和相关信息交回来。

第二项是上下文压缩。长时间执行时，模型需要带着目标、约束、已有结论、变更和验证结果继续工作；这些信息会不断积累，最终碰到 Token 上限。没有压缩时，任务往往不是因为已经完成才结束，而是因为再也装不下前面的过程。

上下文压缩并不是简单地“少记一点”。真正重要的是保住后续行动需要的事实：最初的目标和边界是什么，已经验证了什么，哪些决定不能被推翻，当前做到哪里，以及下一步为什么这样做。它的作用，是让 Agent 在容量接近边界时能够带着这些关键状态继续，而不是被迫从头开始。

这两项改动完成后，整体的运行节奏平稳了许多。偶发异常不再立刻打断流程，Token 的累积也不再必然意味着任务终止。现在，Agent 能更可靠地走完一个完整任务。

不过，这正好也划出了当前能力的边界：它解决了“执行过程不要轻易断掉”，还没有完全解决“复杂任务应如何自己接着往下走”。

## 从一次执行到一段计划

下一步准备加入 Plan 机制。

我希望它不只是把一个大任务拆成待办清单，而是把任务变成一个可持续更新的执行结构：当前目标是什么，已经完成哪些子任务，下一步依赖什么，哪些地方需要验证，遇到失败后应该回到哪一步重新判断。

这样，子任务之间才会有明确的衔接。执行某一步之后，Agent 不必只报告“这一部分完成了”，而可以基于计划判断：现在是否具备进入下一步的条件，是否需要先补一个验证，还是应该因为新发现而调整后续路径。

我可能还会加入空闲检测机制。它解决的不是任务本身的逻辑，而是另一种很常见的中断：系统没有报错，却因为没有新的动作而悄悄停住。发现这种状态后，系统至少应该能够判断这是正常等待、需要恢复推进，还是应该把问题明确交给人，而不是让任务无声地悬在那里。

这些能力仍在计划中。我暂时不把它们当作“自主完成复杂任务”的答案。Plan 只是让过程更连续的骨架，真正可靠的连续执行还取决于状态保存、失败恢复、验证反馈，以及何时应当停止并请求人工介入。

## 长任务也需要过程中的检查点

另一个更偏工作方法的感受，是 Agent 不能只在最后才接受检查。

目前我采用 PDCA 的方式推进：先澄清目标、范围与验收条件；再完成一个最小但完整的阶段；接着根据测试、运行结果或实际产物独立检查；最后把失败、遗漏和新发现转化为下一轮的计划。

为了改善之前遇到的一些执行偏差，我又在任务之间加入了 checkpoint 任务。它不负责继续堆进度，而是提前介入 review：回看当前改动是否仍服务于原始目标，约束有没有遗漏，验证是否足够，下一步是否建立在可靠的事实之上。

这有点像在长途行进中定期确认方向。等到所有子任务完成后再 review，偏差可能已经扩散到很多地方，修正的成本很高。checkpoint 把检查前移，未必能消除错误，但有机会在它还是局部问题时发现它。

这种安排也让 Plan 不只是自动续跑的工具。计划负责给出路径，checkpoint 负责确认这条路径仍然值得走；PDCA 则让每一次检查的结果真正进入下一轮行动，而不是被记录后遗忘。

checkpoint 目前还在观察效果。它会增加一点过程成本，也需要避免把每一步都变成繁琐的停顿。但对于复杂任务而言，我更在意的不是让 Agent 永远不暂停，而是让每一次暂停都发生在有价值、可检查的位置。

## 连续执行不是把人移出流程

让 Agent 更少中断，并不意味着人要更少知道发生了什么。

恰恰相反，任务能持续更久时，目标、计划、当前状态、已验证的证据和异常处理就更需要被清楚地保留下来。否则，它只是从频繁打断人，变成了在更长的一段黑箱过程后交回一个难以判断的结果。

对我来说，长任务能力的价值，是减少那些没有必要的人为衔接：不必因为一次偶发异常重启，不必因为上下文塞满重新解释，不必在每个子任务后手动把工作推向下一步。但目标由谁定义、边界在哪里、何时算完成、哪些风险必须由人决定，这些责任并不会因此消失。

基础工作能力让 Agent 可以完成一个任务；异常重试和上下文压缩让它更不容易在途中掉线；接下来的 Plan、空闲检测和 checkpoint，则是在尝试解决另一件更难的事：如何让一段复杂工作既能连续推进，又始终保持可检查、可修正。

我现在越来越觉得，Agent 的成熟不只取决于它会做多少事情，也取决于它能否把一件事情做得不断线，并在该停下来检查的时候，知道为什么停下来。
