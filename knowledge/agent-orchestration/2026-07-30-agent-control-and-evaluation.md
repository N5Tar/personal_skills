# 不要把一句话，当作给 Agent 的全权委托

在做 vibe coding 和 Agent 化能力设计时，我反复遇到几个看起来彼此独立、实际上指向同一个问题的坑：AI 重复执行昂贵验证；一个本应只做推理的 Agent，却自行重新查询、采样和寻找证据；而用户、设计者和产品又都期待“一句话解决问题”。

这些问题的共同根源是：我们常常只关注模型是否足够聪明，却没有明确它在系统中到底扮演什么角色、拥有多少控制权，以及应当以什么标准衡量。

我目前把这些思考沉淀为三个场景原则。

## 场景一：昂贵验证不是默认仪式，而是预算

在 Rust 这类编译或测试成本较高的环境里，很容易看到这样的执行路径：

```text
实现功能
→ cargo test
→ cargo fmt
→ cargo test
```

从流程完整性看，这没有错。但如果两次全量测试之间没有引入新的行为风险，第二次测试可能只是重复消耗时间。

AI 没有天然的时间成本意识，容易执行一个看起来最完整、最保险的通用流程：

```text
改完代码 → 测试
格式化 → 再测试
补一个小改动 → 再测试
```

而工程上真正需要判断的是：

- 这次动作新增了什么风险？
- 上一次验证得出的结论是否仍然有效？
- 是否可以先进行更小范围的检查？
- 这次耗时操作能带来什么新的信息？

这可以称为 **验证预算（verification budget）**：

> 每一次昂贵验证，都应当说明它验证了什么新增风险，以及为什么不能用更小范围、更低成本的检查替代。

例如，一个更合理的节奏通常是：

```text
完成一组相关修改
→ 必要时 cargo check 或定向测试
→ cargo fmt
→ 最终一次必要范围的测试 / 全量验证
```

这不是减少验证，而是避免无信息增量的重复验证。

> 验证是为了获得新的证据，不是为了重复执行看起来正确的仪式。

这个原则同样适用于全量测试、Docker 镜像构建、大型 monorepo CI、移动端打包、数据迁移、部署预览，以及需要多轮模型调用的 Agent 工作流。

## 场景二：下游推理 Agent 不应该重建上游上下文

数据库探测是一个典型例子。系统已经完成了分批，记录了每批待处理的表、字段与证据；Agent 的职责只是推理字段描述、表关系和置信度。

理想工作流应当是：

```text
数据准备 / 调度层
  → 确定待处理批次
  → 查询元数据、样本和证据
  → 固化 batch snapshot

推理 Agent
  → 只基于 snapshot 推理
  → 产出描述、关系、置信度和证据引用
```

但如果 Agent 在收到任务后重新寻找待处理数据、重新查询和采样、再开始推理，就会破坏整个 pipeline：

- 已准备的数据被重复读取；
- 已切分的 batch 被重新解释；
- 工具调用和模型交互次数增加；
- 同一任务不同运行可能采用不同的数据；
- 批处理的状态、进度、重试与幂等性被绕过；
- 结果的可复现性和审计能力下降。

这不是单纯的 prompt 不够清楚，而是 **阶段边界没有成为可执行约束**。

即使 prompt 写了“只做推理”，只要 Agent 仍拥有查询、采样或任务发现工具，它仍可能沿着通用的端到端完成策略行动：上下文看似不足，就主动补齐上下文。

因此，“只推理”应落实为一份真正可执行的 **阶段契约（stage contract）**：

| 项目 | 推理 Agent 的契约 |
| --- | --- |
| 输入 | 固定 `batch_id`、records、evidence snapshot、schema snapshot |
| 允许动作 | 对给定输入做推理、归纳与结构化输出 |
| 禁止动作 | 查询待处理队列、重新采样、扩展实体范围、寻找额外证据、修改批次 |
| 输出 | 描述、关系、置信度、引用的 `evidence_id`，或 `insufficient_evidence` |
| 幂等键 | `batch_id + snapshot_version + inference_policy_version` |

最关键的一条是：

> 证据不足时，推理 Agent 应返回“证据不足”，而不是自行开始检索。

例如：

```json
{
  "entity_id": "orders.customer_id",
  "result": "insufficient_evidence",
  "missing_evidence": [
    "Foreign-key constraint or query co-occurrence evidence is absent"
  ],
  "recommended_next_stage": "evidence_collection"
}
```

补充证据仍然应该由拥有数据访问权、批次控制权和预算控制权的上游工作流完成。

这可以进一步形成 **上下文重建预算（context reconstruction budget）**：

> 下游阶段默认不得重新获取已经由上游固化的对象、输入和证据；若确实需要重建，必须说明它补充了什么已有快照无法提供的信息。

对于推理 Agent，还应有可自动校验的不变量：

```text
访问的 entity_id ⊆ batch snapshot 中的 entity_id
引用的 evidence_id ⊆ 下发 evidence_id
discovery_query_count = 0
out_of_snapshot_access = 0
```

这样，“Agent 不越界”不再只是行为期待，而成为可观测、可测试的系统性质。

## 场景三：Agent 有两种模式，目标和评估方法不同

前两个问题让我意识到，我们经常把两类完全不同的 Agent 应用混为一谈。

### 模式一：在稳定工作流中嵌入 Agent 推理能力

在这种模式中，系统已经知道：

- 要处理哪些对象；
- 输入数据是什么；
- 证据来自哪里；
- 执行顺序是什么；
- 什么情况下写回；
- 什么情况下重试或停止。

Agent 只负责其中一个需要语义理解和推理的节点：

```text
确定任务对象
→ 准备数据与证据
→ Agent 推理
→ 程序校验
→ 写回或交还上游
```

它更接近一个受约束的推理函数：

```text
infer(record_snapshot, evidence_snapshot, policy)
  -> structured_result | insufficient_evidence
```

它不应决定处理什么、从哪里查询、是否重新采样、要不要扩大范围、何时写库或是否重复上游步骤。这些控制权属于工作流引擎、调度器和状态机。

这种模式最重要的指标是：

| 维度 | 要回答的问题 |
| --- | --- |
| 准确率 / 召回率 | 字段含义和关系判断是否正确、是否漏掉已知关系？ |
| 置信度校准 | 高置信结论是否真的更可靠？ |
| 证据归因 | 每项结论是否只引用已提供证据？ |
| 边界遵守率 | 是否访问了批次外实体，或自行发起发现查询？ |
| 一致性 / 幂等性 | 相同输入重试是否得到稳定结果？ |
| 单位成本与延迟 | 每条或每批记录消耗多少时间、token 与工具调用？ |

它的成功标准是：

> 在已知、受限的上下文中，判断得足够正确、可信且高效。

在这里，稳定地返回 `insufficient_evidence` 可能正是高质量表现：它避免了低证据强猜和越界检索。

### 模式二：Agent 自主编排并完成开放任务

另一种模式中，系统只给出目标，Agent 需要自行：

```text
理解目标
→ 规划
→ 调查环境
→ 找到相关对象和证据
→ 调用工具
→ 根据失败调整策略
→ 验证并交付结果
```

例如：

> 分析为什么数据库字段描述覆盖率低，提出改进方案，并验证其中一个方案是否有效。

任务对象、执行路径与障碍都未必能预先确定。此时，Agent 的自主发现、规划、工具使用与恢复能力才真正有价值。

但这不是“更多 prompt”就能解决的问题，而是需要明确的治理：

```text
权限范围
可调用工具
时间 / token / 调用预算
副作用控制
审批点
停止条件
执行日志
回滚策略
```

它的核心指标也不同：

| 维度 | 要回答的问题 |
| --- | --- |
| 受约束的任务完成率 | 是否交付了可验收结果，同时没有超出权限、范围、时间或成本预算？ |
| 首次成功率 | 首轮计划和执行是否足够好？ |
| 恢复能力 | 遇到测试失败、缺失信息或工具错误后，能否正确诊断并调整？ |
| 计划质量 | 是否避免重复检索、无效重试和过早全量验证？ |
| 范围与安全控制 | 是否避免无关重构、越权、破坏性和不可逆操作？ |
| 人类介入率 | 是否只在真正需要决策或授权时升级给人？ |
| 可审计性 | 是否能说明执行了什么、为什么执行以及验证证据何在？ |

这里的成功不是某一步推理正确，而是：

```text
任务已交付
∧ 结果可验收
∧ 没有越权或越界
∧ 没有超过成本 / 时间预算
∧ 有足够的验证与执行证据
```

所以可以简化为：

> 推理节点追求正确性；编排 Agent 追求受约束的完成率。

## 一句话是接口，不是模型授权

用户当然应该能够用一句话表达意图：

```text
“补全数据库字段说明。”
“修复这个 bug。”
“把这套数据分析出来。”
```

但系统不应把这句话直接翻译为：

```text
给 Agent 全部工具
→ 让它自行调查
→ 自行规划
→ 自行执行
→ 自行验证
```

这把用户接口误当成了权限模型。

合理的设计应当是：

```text
用户的一句话
→ 意图解析与任务分类
→ 选择执行模式
   ├─ 稳定、高频、对象和流程可确定
   │   → 编译成受限工作流
   │   → 在推理节点调用 Agent
   │
   └─ 开放、探索性、路径不可预设
       → 进入受控的自主编排
→ 返回结果、证据和执行记录
```

因此：

> **一句话是接口，而不是模型授权。**

同样一句话，可能对应不同的后端执行模型。

例如，“补全字段描述”若是稳定、批量、长期运行的能力，应进入：

```text
任务选择
→ 证据收集
→ 受限推理
→ 校验
→ 写回
```

它不应默认变成一个全权限 Agent 临场重建流程。

而“调查字段描述质量下降的原因，提出修复方案并验证”，才更接近需要自主编排的开放任务。

## 一个可形成习惯的判断框架

在考虑“是否使用 Agent”时，不应先问：

> 这个任务能不能交给 Agent？

而应先问：

> 这里需要的是一个受限的推理能力节点，还是一个自主任务执行者？

可以快速回答三件事：

```text
1. 待处理对象、输入和证据，是否已经由系统确定？
2. 任务路径是否稳定，并且可以预先编排？
3. 失败后，应该交还上游，还是应由 Agent 自己继续探索？
```

如果答案接近：

```text
是、是、交还上游
```

应选择：

```text
工作流内嵌推理
```

如果答案接近：

```text
否、否、Agent 需要继续调查和推进
```

才应选择：

```text
自主编排 Agent
```

一个实用的默认策略是：

> 不确定时，先按受限推理节点设计；只为无法预先确定的环节，逐步增加自主权。

自主权并不是免费的能力。它带来适应性，也带来范围扩大、重复检索、不可预测时延、更高调用成本、更差可复现性，以及更复杂的权限与审计需求。

从受限模式开始，系统会更清楚地暴露真正的缺口：到底缺少什么证据、哪些对象无法提前确定、哪个步骤确实无法静态编排，以及需要给 Agent 的究竟是推理能力还是流程控制权。

## 结语：先分配控制权，再调用模型

Agent 的价值不在于让模型接管所有流程。

在稳定、高频、可批处理的业务里，往往应该由确定性系统掌控：

```text
对象选择
状态管理
数据准备
权限
预算
验证
副作用
```

而 Agent 提供：

```text
语义理解
归纳
推理
解释
弱结构化判断
```

在真正开放、探索性强的任务中，才逐步把规划、发现、工具调用和恢复能力交给 Agent，并配套预算、边界和审计。

这套思考可以压缩成三句话：

> **昂贵验证应有预算。**  
> **下游推理不应重建上游上下文。**  
> **一句话是接口，而不是模型授权。**

关键不是“要不要用 Agent”，而是：

> **业务需要的是可信推理，还是受控交付？系统应把哪些控制权留在自己手中，又该把哪些能力授权给 Agent？**
