# 当 Agent 开始修改自己，它已经开始帮我干活了

最近在做一个属于自己的 Agent。

它的能力还很基础：能执行命令，能读取和编辑文件。没有很丰富的工具生态，没有复杂的记忆系统，也没有打磨成熟的交互界面。按照我们对成熟 Agent 的想象，它显然还有很多“不完善”的地方。

但这几天，我开始让它处理一些关于它自身的改进需求。

我提出需求，它读取自己的代码，完成一轮修改，执行命令检查结果；改完之后重启，新的 Agent 就带着这次改动继续工作。这个过程并不戏剧化，甚至和它修改任何一个普通项目没有本质区别。但我是在这时意识到：它当然还不完善，可它已经开始帮我干活了。

这让我反复思考一个问题：一个 Agent 到底需要多少能力，才算真正有用？

## 不是功能足够多，而是闭环已经成立

谈 Agent 时，我们很容易先看功能清单：有没有联网能力，有没有浏览器，有没有多模态输入，有没有长期记忆，有没有多个子 Agent，有没有精致的任务面板。

这些能力都重要。它们决定了一个 Agent 能覆盖多大的范围、处理多复杂的任务，也决定了人能在多大程度上放心地使用它们。

但它们未必是一个 Agent 第一次产生价值的前提。

对我来说，真正的临界点不是它又学会了一个新工具，而是它形成了一条完整的工作闭环：

> 理解目标 → 读取现状 → 改变状态 → 获取反馈 → 根据反馈继续行动

这件事说起来很朴素，放在软件开发里却很有力量。

需求给了它目标；源码、配置、日志和测试输出让它看到现状；编辑文件和执行命令让它能够行动；构建、测试和运行结果提供反馈；如果结果不对，错误信息又会成为下一轮修改的依据。

当这条链路走通时，Agent 就不再只是回答“你可以怎么做”。它开始真的做一些事，再把可以检查的结果交回来。

对程序员而言，软件工程本身是一个特别适合 Agent 介入的环境。代码大多存在文件里，构建和测试大多可以通过命令触发，失败也通常会留下日志和堆栈。文件系统与命令行，已经把工作对象、操作方式和反馈信号标准化了很大一部分。

所以，命令执行和文件编辑看起来只是两个很简单的能力，实际却覆盖了开发工作中一块很重要的操作面。

这当然不是所有 Agent 的通用答案。做研究、客服、设计或线下执行，需要的感知和行动能力都不同。但在软件开发这个具体场景里，一个足够短的闭环，已经足以让一个基础 Agent 进入真实工作流。

## 能修改自己，不等于会自我进化

“它可以修改自己的代码”听上去很容易让人联想到自我进化。

我更愿意把这两件事分开。

第一种是**自修改**：人在前面给出需求、约束和验收标准，Agent 在自己的工程里定位问题、修改实现、运行验证。它做的仍然是一项软件任务，只不过任务对象恰好是它自己。

第二种才是**自我改进**：它能够自己发现真正的问题，判断什么值得改，评估改动的成本和副作用，避免局部优化造成整体退化，并长期保持正确的方向。

后者困难得多，也远不是“能改自己的文件”就能解决的。

但前者已经足够改变协作关系。以前，我在实现一个工具；到了这个临界点之后，我开始把一部分实现工作交给它，并和它一起迭代同一个系统。

这并不意味着人可以退出。目标仍应该由人确定，权限边界仍应该由人划定，完成与否也仍应由人或明确的验证机制来判断。Agent 可以承担探索、修改和重复验证，但它不应该替人含糊地决定“什么才是值得做的事”。

我真正感受到的，不是它突然拥有了某种神奇的自主性，而是任务开始可以在我和它之间流动：我给出方向和边界，它处理其中一部分实现与验证，再把结果和证据交回来。

## 为什么我的关注点开始变化

在闭环还没有建立时，最自然的问题是：它还能不能再多做一点？再加一个工具，会不会更强？能不能让它访问更多信息、执行更多操作？

但当它已经能完成一部分真实工作后，我关心的问题变了。

我开始在意：一次工具调用，到底应该向人展示哪些输入和输出？长日志应该完整展开，还是先给结论、再允许追溯原始证据？上下文很长时，怎样压缩才不会丢掉目标、约束和已经验证过的事实？不同任务的工作空间该如何隔离？哪些内容不应该被复制？哪些操作必须得到确认？任务中断后，能不能知道它已经做了什么、还差什么，并从那里继续？

这些问题看上去像产品体验细节，实际上决定了一段人机协作是否可信。

一个可以执行很多动作、却让人看不清过程的 Agent，很难被放心地交付更重要的工作。一个会压缩上下文、却丢掉关键约束的 Agent，可能比没有记忆更危险。一个能改动文件、却不能清楚展示改了什么、为何而改、是否验证过的 Agent，也很难进入长期使用。

所以，功能越过最小门槛之后，下一阶段未必是无限增加能力，而是建设协作的基础设施：让过程可观察，让行为可控制，让变更可审阅，让失败可恢复。

成熟的产品之所以显得“完整”，很多时候也正是在补齐这些部分。它们并不只是让 Agent 多会一点，而是在让一段可能出错、可能中断、可能涉及真实代价的协作，变得更稳定、更清楚，也更值得交付。

## “够用”的定义，也许比想象中更早到来

我以前会把“一个成熟的 Agent”想成能力非常完整的系统：会很多工具，适配很多场景，能处理很长的任务，也有完善的界面和安全边界。

现在我依然认为这些都值得做。它们会扩大 Agent 可以覆盖的工作范围，也会扩大我愿意信任它的范围。

但我不再觉得必须等到这些全部具备，Agent 才算有用。

只要它能在一个可控的环境里，把一个目标变成一串可以验证的行动；只要它能从结果中继续调整，而不是把每一步都重新抛回给人；只要我能看见、检查并在必要时接手这段过程，它就已经开始成为一个协作者。

也许一个 Agent 需要的最小能力，从来不是某个固定数量的工具。

它需要的，是一条足够短、足够真实的工作闭环。

当这条闭环成立之后，我们面对的问题就不再只是“怎么让它再多会一点”，而是更值得认真对待的那个问题：怎样让我们更好地一起工作。
