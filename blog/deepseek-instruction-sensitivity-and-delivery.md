# 当对话本身就是交付物：一次 DeepSeek 异常工具调用的排查

这几天一直在调试 DeepSeek。

起因是我发现，它在输出结果时总会做一些奇怪的小动作。明明已经到了最后输出结论的阶段，它却会先输出一段结论，然后同时发起一个没有实际意义的 function call，比如：

```text
bash(echo done)
bash(echo ok)
bash(echo finally answer)
```

这些调用既没有获得新的信息，也没有改变任何有意义的状态。单独看，它们似乎只是模型多做了一个无关紧要的动作，但放在实际的对话交付链路里，问题就没有这么简单。

一个本应完整输出的答案，会因为这次工具调用被截断。工具执行结束后，模型再继续生成剩余部分。原本的一次回答，由此被切成多个续写任务，直到最后才真正输出完成。

这不仅影响阅读体验，也会直接影响工程实现：系统应该把哪一段看作最终结果？前后的文本应该拼接、覆盖，还是分别展示？富文本组件何时可以认为已经完整？一次回答被拆成多个消息和工具事件之后，原本清晰的结果边界也变得模糊了。

## 一开始，我怀疑是 A2UI 的增量更新

我的场景中，DeepSeek 会调用一个数据分析 Skill，这个 Skill 又依赖了一个负责富文本输出的 A2UI Skill。最终的数据分析结果，需要通过 A2UI 的形式展示出来。

最初，我怀疑问题来自 A2UI 的 `create/update` 增量更新机制。因为在这种模式下，结果本来就可能经历创建、补充和更新，模型也许因此倾向于把一次输出拆成多个阶段。

于是我把它改成了 v1.0 的首屏全量加载，希望模型一次生成完整内容，不再持续更新。但修改之后，情况并没有得到明显改善。即使不再依赖增量更新，DeepSeek 仍会在结论附近插入类似 `echo done` 的无意义调用。

这说明问题可能不在 A2UI 的加载方式，而在更靠前的指令中。

## 真正产生影响的，是一段自检要求

后来在和 AI 讨论及反复测试的过程中，我注意到给 DeepSeek 的指令里存在一段自检机制。这段自检要求它确认：

- 数据是否已经完成分析；
- 任务是否已经完成；
- 最终结果是否以 A2UI 形式输出；
- 输出是否满足相应的完整性要求。

这些要求从设计意图上看没有问题。它们希望模型在交付前检查结果，避免漏掉分析或输出格式。但实际运行时，DeepSeek 似乎会给这类指令较高的执行权重，并把“确认已经完成”理解成一个需要显式执行的动作。

于是，当内容实际上已经准备完成，它仍然会寻找一个动作来表示自己做过检查。`bash(echo done)`、`bash(echo ok)` 这类调用，可能就是这种要求下成本最低的动作：它们看上去完成了某种确认，却没有任何真正的业务意义。

我尝试删除这段自检要求后，问题得到了明显改善。虽然这还不能概括 DeepSeek 在所有场景下的行为，但至少在这次排查中，A2UI 的增量更新并不是主要原因。更值得关注的是，模型如何理解 Skill 中关于“检查”和“完成”的指令。

我暂时把这个现象称为 **DeepSeek 对指令的敏感性**，为什么是DeepSeek?因为其他模型没有遇到这个问题，minimax除外，它根本不听指令。
这里的“敏感”并不只是它更严格地遵循指令，而是某些自检或完成性指令，可能会改变它对整个任务流程的理解，甚至让它在本应结束的时候继续寻找可以执行的动作。

## 这套工作方式，其实更像在处理本地文件

继续思考之后，我发现，这种“先生成结果，再做后置检查”的机制并非天然有问题。它非常适合以本地文件为产物的任务。

例如，一份分析报告需要写入文件时，完整流程可以是：

```text
生成结果文件
→ 重新读取文件
→ 检查内容和格式
→ 必要时修改
→ 验证完成后告知用户
```

在这个过程中，文件是一个已经生成、可以重复访问的独立产物。后续的读取、检查和修改都围绕这份文件进行。即使模型在生成文件后继续调用多个工具，也不会把交付物本身切碎。

因为真正的结果已经落在文件里。最后的对话文本只需要告诉用户：产物在哪里、做了什么检查、当前状态如何。它更像一份交付说明，而不是结果本身。

但对话中的交付方式不同。

在很多 ReAct 风格的交互中，前面的分析、工具调用和观察都属于执行过程，最后一段文本才是交给用户的结果。这里没有一份预先存在的结果文件，可以在输出之后继续检查。**最后的文本本身就是交付物。**

这时，如果仍然沿用文件任务中的工作方式：

```text
生成结果
→ 输出结果
→ 检查是否完成
→ 再执行一个动作
→ 继续输出
```

那么“输出结果”发生的那一刻，交付其实已经开始了。后置动作并不是在检查一个独立产物，而是在交付过程中把产物切开。

从模型视角看，它可能只是多完成了一次自检；从工程视角看，一个完整答案已经被拆成了多个步骤。

## 交付方式决定了检查应该发生在哪里

这次问题让我开始更明确地区分两种任务。

一种任务的结果会落在文件、数据库、页面或其他可再次访问的对象里。对这类任务，可以先生成产物，再围绕产物执行检查和修正。对话里的最终回复只是交付说明。

另一种任务直接在对话中交付结果。最终回复不是一张指向产物的回执，它自己就是产物。在这种情况下，分析、自检和格式确认都应该发生在组织最终回复之前。一旦开始输出正式结果，就不应该再把它当成一个仍需后置处理的中间步骤。

两种方式的差别可以简单概括为：

```text
文件交付：生成产物 → 检查产物 → 告知结果
对话交付：检查已有结果 → 组织内容 → 完整交付
```

这里真正重要的不是“要不要自检”，而是自检针对什么对象，以及它发生在交付之前还是之后。

如果检查对象是一份文件，那么生成之后检查很自然；如果检查对象是即将发给用户的回答，那么检查应该在回答开始之前完成。否则，Skill 中一句看似合理的“输出后确认结果是否完整”，就可能在对话任务里制造出完全不同的行为。

## Skill 需要有交付产物的意识

这也让我重新思考 Skill 应该如何设计。

过去设计 Skill 时，我们往往更关注它具备什么能力：能不能分析数据，能不能生成图表，能不能以 A2UI 的形式展示。但仅仅描述能力还不够。Skill 还需要知道，自己的结果最终通过什么方式交付。

如果一个数据分析 Skill 的结果要写入文件，那么它可以在生成后重新读取、校验和修正。如果它的结果要直接出现在当前对话中，那么同样的后置检查机制就不一定适用。

尤其是在 Skill 存在依赖关系时，这一点更容易被忽略。

我的数据分析 Skill 依赖 A2UI Skill，本意是使用它的富文本表达能力。但 A2UI Skill 中如果还包含创建、更新、完成确认和输出后检查等工作方式，这些内容也可能随着依赖一起进入模型的指令上下文。

于是，上层 Skill 原本只是希望复用一种输出形式，最终却连同下层 Skill 对“产物如何生成、如何检查”的假设也一起继承了。

这说明 Skill 的依赖不只是能力的组合，也可能是工作模式的叠加。一个 Skill 提供某种输出能力，并不意味着调用它的任务就拥有相同的交付方式。格式可以被复用，但围绕格式形成的生成、更新和检查流程，未必适合所有上层任务。

所以在设计 Skill 时，我认为至少要先回答几个问题：

```text
这次任务真正交付的产物是什么？
产物存在于文件中，还是存在于最终对话里？
哪些检查必须在产物生成后进行？
哪些检查必须在正式交付前完成？
被依赖的 Skill 提供的是能力，还是连同工作流程一起提供？
```

这些问题不一定需要变成一套复杂的新协议，但需要成为 Skill 设计中的明确前提。否则，一个原本为本地产物设计的自检机制，很容易被原样带进对话交付场景，并在模型的严格执行下变成多余的工具调用。

## 结果在哪里，决定了工作如何结束

回头看这次排查，`bash(echo done)` 本身只是一个很小的现象。真正的问题是，模型收到的指令没有清楚地区分“结果已经写入一个独立产物”和“结果正在通过这段对话交付”。

在前一种场景里，结果生成后继续操作是正常工作；在后一种场景里，最终文本一旦开始输出，交付就已经发生。继续调用工具，会改变这份结果在工程上的完整性。

删除自检指令能够明显改善问题，但这次调试带给我的思考并不只是“少写一段自检”。更重要的是，在设计 Skill 时，需要先建立交付产物的意识，再决定生成、检查和结束任务的方式。

同一句“检查是否完成”，放在文件交付和对话交付中，可能代表完全不同的动作。

而 Skill 是否理解这种差别，会直接影响 Agent 能不能在正确的时刻停下来，把一个完整结果交到用户手上。
