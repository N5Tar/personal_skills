# 配置不是表单状态：一次 Agent 工具热更新排查带来的提醒

这次排查从两个看起来很小的问题开始：为什么 `/configs` 首页不能用上下键选择？为什么在配置页保存了工具，运行时却没有立即生效？

前一个问题像是 UI 细节，后一个问题像是“少调了一次刷新”。但沿着代码往下看，我发现它们都指向同一个容易被忽略的事实：配置不是页面上的表单状态，也不只是磁盘上的 JSON。它是一条会进入运行时、改变能力边界的链路。

当这条链路只有一半被实现时，界面看起来可以操作，配置也确实写进了文件，但系统实际运行的还是旧世界。

## 一个能保存的配置，不等于一个生效的配置

工具配置页当时的行为很直观：用户勾选工具，点击保存，`.myagent/config.json` 被更新，TUI 内存里的工作区配置也同步更新。

从页面角度看，事情已经完成了。

但 Agent 不是每次调用工具时才去读取配置文件。它会在构建时根据 `enabled_refs` 建立工具注册表，并把可用工具的 schema 交给模型。也就是说，运行中的 Agent 已经持有了一份具体的能力快照。

因此，配置文件变了，不代表这份快照变了。

如果保存之后没有通知 Gateway 重载配置并重建后续会话使用的 Agent，那么用户得到的体验就是最危险的一种：界面告诉他“保存成功”，文件也证明“保存成功”，但模型仍然看不到新工具。

这不是单纯的刷新遗漏，而是把“持久化成功”和“运行时生效”混成了一个状态。

## 配置变更真正经过了哪些边界

这次梳理后，工具配置至少跨越了四层：

- TUI：编辑、校验、展示保存结果。
- Workspace：将配置安全地持久化到工作区。
- Gateway：接收配置刷新请求，重新解析当前工作区配置。
- Agent：以新的工具注册表构造后续执行所需的能力快照。

这四层各自都有合理的职责，问题不在于层次多，而在于不能默认上一层完成就意味着下一层已经完成。

更准确地说，保存是一项状态变更；刷新是一项运行时变更。前者保证数据留下来，后者保证新数据进入未来的执行路径。两者必须被明确连接，而不是依赖重启、重新连接或偶然创建的新 session 来补上。

这也解释了为什么“改配置要不要重启”不是一个纯粹的产品问题。它首先是架构问题：系统是否知道哪些对象缓存了配置派生出来的状态？配置变化时，哪些对象应该继续使用旧快照，哪些新对象必须使用新快照？

## 热更新不等于修改正在执行的任务

一开始很容易把“实时生效”理解成：保存以后，所有正在运行的任务都立刻换成新工具集。

这通常不是一个好目标。

一次 Run 开始后，它的模型、工具、权限和上下文应该尽量稳定。中途替换工具注册表，意味着同一个 Run 前后看到的能力集合不同；这会让工具调用、审计和错误恢复都变得难以解释。

更清晰的语义是：

- 已经开始的 Run 保持自己的执行快照。
- 保存配置后，Gateway 刷新工作区配置。
- 后续创建的 session 或后续启动的 Run 使用新配置。

这样既满足“不需要重启”的预期，也不牺牲执行过程的确定性。

所谓热更新，重点不是让一切在同一瞬间改变，而是让系统明确区分过去已经开始的工作和未来即将开始的工作。

## UI 的小缺口会暴露状态模型的缺口

配置首页不能上下选择的问题也很有代表性。

按键层其实已经把 `Up` 和 `Down` 转换成了选择意图；问题出在首页没有保存“当前选择项”这个状态，reducer 也没有处理首页的选择迁移。渲染层最终只能把 `Tools`、`Context`、`Models` 写成固定文本，Enter 也只能固定进入第一个页面。

从实现上说，这只是少了一个字段和几条状态转换。

但从产品语义上说，它提醒我：交互不是按键映射的集合，而是可观察状态、状态转换和渲染结果的闭环。只实现输入事件，或只实现静态界面，都不算一个完整的交互。

这和工具热更新其实是同一种问题：系统的一端已经发生了变化，另一端却没有建立相应的状态连接。

## 工作区身份同样属于运行时上下文

本次会话还有另一个相关的改动：新建 session 的系统提示会注入当前工作区根目录；全局 `agent.md` 与项目内 `.myagent/agent.md` 按固定顺序叠加。

这件事表面上是在补提示词，实际上是在明确 Agent 的工作边界。

模型如果不知道自己面向哪个工作区，就很难正确理解相对路径、项目内规则和可操作范围。项目内的 `agent.md` 如果覆盖了全局说明，或者工作区初始化时覆盖了用户已有的说明文件，配置体系就会从“约束 Agent”变成“意外抹掉 Agent 的上下文”。

因此，这里的原则不是把所有信息塞进 prompt，而是让每一种信息都有清楚的来源和合并规则：

- 全局说明提供所有项目共享的工作方式。
- 工作区说明提供项目附加约束，而不是替换全局说明。
- 工作区根目录提供当前执行的环境边界。
- 已创建 session 保存自己的系统消息，避免历史会话在中途悄悄改变语义。

配置、提示词和运行时快照在这里汇合了：它们都需要可追踪的来源，也都需要明确“何时生效”。

## 不要让重启成为隐式的配置协议

很多开发工具早期都会形成一种约定：配置改了不生效就重启。这在开发期很方便，因为它绕过了失效、刷新和生命周期的问题。

但如果重启成了默认路径，系统就等于把最重要的状态转换藏在了进程重建里。用户不知道哪些操作需要重启，开发者也无法明确保证一次保存到底改变了什么。

更好的方式不是追求无限制的动态修改，而是把配置协议说清楚：

- 保存会校验并持久化什么。
- 保存后 Gateway 会刷新什么。
- 哪些未来任务会采用新配置。
- 哪些进行中的任务仍固定使用旧快照。
- 刷新失败时，界面应如何如实反馈，而不是显示模糊的“已保存”。

当这些语义被写进边界，重启就重新变成一种运维行为，而不是功能正确性的前提。

## 这次的结论

这次没有发现一个特别复杂的算法问题，反而是几个很具体的工程细节让我重新确认了一件事：配置本身不是能力，进入运行时的配置才是能力。

一个配置系统是否可靠，不取决于它能否写文件，而取决于它是否能回答这些问题：

- 新配置由谁加载？
- 哪些运行中对象持有旧快照？
- 新配置从哪一个执行边界开始生效？
- 用户如何知道保存、刷新和生效分别是否成功？

把这些问题想清楚，Tools 保存后是否需要重启、TUI 页面是否能选择、工作区说明如何叠加，就不再是零散的补丁。

它们会回到同一件事上：让配置从静态文件，成为有清晰生命周期和边界的运行时契约。
